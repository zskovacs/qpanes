# QPanes — Coding agent instructions

QPanes is a lightweight, keyboard-first, cross-platform, dual-pane desktop file manager inspired by the workflows of Total Commander. It is an independent implementation, not a reverse-engineered or copied version.

## Stack and source of truth

- Desktop: Tauri 2. Frontend: Svelte 5 + TypeScript, using the generated project's existing Vite/SvelteKit tooling. Backend: Rust.
- Development: Linux under WSL/WSLg; supported release targets: Windows, Linux, macOS. Do not assume that passing Linux tests verifies Windows/macOS behavior.
- Read `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, `docs/ROADMAP.md`, and the active `docs/slices/*.md` before doing significant work.
- Respect the versions, folder structure, and scripts already generated by create-tauri-app. Do not migrate away from SvelteKit if the generated template uses it; configure its static client-side output correctly for Tauri.

## Architecture

- Rust owns filesystem access and semantics. Svelte owns presentation, input handling, and view state.
- Keep Tauri commands/adapters thin; reusable filesystem/domain logic must not depend on Tauri or UI components.
- Prefer extracting a small Rust core crate when implementing actual filesystem functionality, without introducing remote-provider/plugin/MCP abstractions before they are needed.
- Use typed IPC request/response data. Never let the frontend call arbitrary shell commands or circumvent the intended Rust API.
- Treat paths, permissions, symbolic links, and non-UTF-8 filenames as cross-platform correctness concerns; handle failures explicitly, without panics.
- Avoid blocking the UI with filesystem I/O. Handle rapidly repeated navigation and stale asynchronous responses.
- Keep the application local-first, fast at startup, and with a small dependency footprint.

## User experience

- The two panels must operate independently, with clear active panel and selection state.
- Keyboard navigation is first-class, not an afterthought. Test focus behavior, selection, sorting, keyboard shortcuts, error/empty/loading states.
- Implement an intentional, cohesive desktop UI rather than a generic dashboard. Maintain a small design-token palette and accessible focus indicators.
- For large directories, evaluate DOM virtualization and Rust-side I/O cost. Do not add data-heavy abstractions without a measured need.
- Use the official Svelte plugin/autofixer when touching `.svelte`, `.svelte.ts`, or `.svelte.js` code, if available.

## Development discipline

- Work one approved slice at a time. Do not add terminal, MCP, remote filesystems, plugins, or write operations in Slice 001.
- Before implementation of a significant slice, record a reviewable slice design/plan in `docs/slices/` using the coding agent's native planning and task tracking; Superpowers is no longer required. Obtain approval of that design/plan unless the user explicitly authorizes proceeding directly to implementation. GOAL mode is for verified implementation against that approved scope.
- Prefer existing maintained libraries where they reduce risk, but verify current APIs and licenses; don't invent dependencies. Avoid copying GPL code into this project.
- No destructive tests against real user files. Use generated temporary fixtures for all write/delete tests in future slices.
- Never change unrelated files; never add secrets or credentials to the repo. Do not disable security controls to simplify testing.
- Record architectural decisions in `docs/ARCHITECTURE.md` only when a decision is made, not as speculative plans.
- Do not claim a feature is finished because it compiles: prove behavior with tests and, for GUI behavior, a real or appropriately labeled mocked UI check.
- Before requesting merge, run and report appropriate commands: `mise run ui-build`, `mise run rust-fmt`, `mise run rust-clippy`, `mise run rust-test`. If project scripts differ, fix these tasks rather than silently skipping them.
- If a command cannot be run, state precisely which verification is missing and why; do not present it as passed.
- End each slice with a concise handoff: files changed, acceptance criteria status, commands and outcomes, risks, manual QA still needed.

## Documentation and Browser Tools

### Context7
- Use the installed Context7 CLI and find-docs skill.
- Retrieve current documentation before using unfamiliar
  or version-sensitive Rust, Tauri or Svelte APIs.
- Do not rely on outdated API knowledge.
- Prefer official documentation when available.

### Playwright
- Use the installed Playwright CLI and skill.
- Prefer CLI over Playwright MCP.
- Verify UI changes through browser interaction.
- Test keyboard navigation, focus behavior and layouts.
- Capture screenshots for significant visual changes.
- Do not treat browser tests as native Tauri E2E tests.

### Verification
- Run relevant tests after implementation.
- Never claim tests passed without executing them.
- Report any tests that could not be executed.
