## DPI investigation and strategy

- Existing stack: Tauri 2.12.5, Tao 0.37.2, Wry 0.57.1. Before this slice there was no application zoom, DPI listener, or window-size loop. Existing dimensions are logical units; this slice adds observation only.
- This session runs Linux GTK/WebKitGTK under WSLg 1.0.79, not a native Windows WebView2 application. WSLg exposes `rdp-0` at 5120×1440 and `rdp-2` at 3840×2160; the requested 2560×1440 display is not the currently exposed first output.
- `/mnt/wslg/weston.log` records `enable_hi_dpi_support = 1`, `enable_fractional_hi_dpi_support = 0`, and `enable_fractional_hi_dpi_roundup = 0`. RDP monitor attributes report desktop scaling 100% for the first output and 150% for the 4K output. Baseline native `available_monitors` reports scale 1 for both; `scaleFactor()` and WebKit `devicePixelRatio` are 1, rows are 32 CSS pixels and CSS zoom is 1.
- Six real window moves between these outputs (three round trips) retain `scaleFactor = 1`, `devicePixelRatio = 1`, 32 CSS-pixel rows, zoom 1, 900×600 physical window contents and the right pane's focus. Maximizing on the 4K output produces 3840×2160 content. The separate baseline maximize/restore check retains the original window dimensions. No true scale-change event can be inferred from these equal reported factors.
- The measured loss of the 150% preference occurs before Qpanes receives monitor information. This explains the small UI in this WSLg setup; it is not evidence of a Qpanes zoom defect or a native Windows WebView2 defect. WSLg's disabled fractional scaling is the identified boundary limitation, supported by compositor logs plus native monitor/WebView measurements. Resolution alone cannot recover the missing OS preference.
- Resolution counts physical pixels; physical density relates those pixels to display size; OS display scaling expresses the user's logical-size preference. Tauri's factor converts logical to physical window units. CSS pixels describe layout, while `devicePixelRatio` describes rasterization relative to those pixels. WebView zoom is a separate content multiplier. Multiplying any of these indiscriminately can double-apply scale. A 4K display does not imply 200%.
- The installed Tao Windows backend enables per-monitor V2 DPI awareness, with older API fallbacks. WebView2 normally detects monitor-scale changes; macOS WKWebView and Linux WebKitGTK use their native backing/GTK scaling. Keep these defaults. Source/documentation inspection establishes the strategy, not target-native verification.
- `scaleFactor()` and `onScaleChanged()` are used only to refresh the observed window snapshot, alongside `onResized()`. The event's physical size is deliberately not reapplied as logical size. The application sets no zoom, CSS scale, position or size in response. Repeated notifications cannot compound scale. The virtual list remains based on 32 CSS-pixel rows.
- No production or development-launcher scaling override was added. A global `GDK_SCALE=2` is useful only as a separate startup test; it is not a per-monitor correction and would enlarge both displays. Environment-specific WSLg configuration can be investigated separately using Microsoft's version-specific options; this slice did not change `.wslgconfig`, Windows display settings, restart WSL, or force a global scale.
- A separate actual `GDK_SCALE=2` native launch reports Tauri factor 2 and WebKit DPR 2, with 2400×1560 physical content for the unchanged 1200×780 CSS viewport, 32 CSS-pixel rows and zoom 1. Thus native GTK/WebKit scaling works when GTK receives a factor; this test does not prove live monitor DPI changes or provide a mixed-monitor workaround.

## Window behavior and platform differences

- `WindowHeader.svelte` reuses the original header and read-only indicator; no stacked header or file-pane redesign. The brand and status badge pass pointer hits to the drag region. Buttons have no drag attributes, accessible labels/tooltips and visible keyboard focus. Pointer activation prevents default focus transfer; Escape from a keyboard-focused control returns to the active pane. Async completion never refocuses a pane.
- Windows/Linux buttons call supported `minimize()`, `toggleMaximize()` and `close()` APIs; close remains a normal close request, not force-destroy. Maximize state is refreshed for external resize/scale events as well as button activation. Late/stale reads and listener teardown are covered by focused tests.
- Tauri's built-in drag region supplies platform-specific dragging/double-click handling. Its runtime supplies native undecorated resize hit testing; real right-edge and corner resizing passed in GTK. No manual resize loop, hit-box overlay or extra resize permission exists.
- macOS retains native traffic lights, native fullscreen/Spaces behavior and decorations via `tauri.macos.conf.json`; `Overlay` removes the extra visual title area and `hiddenTitle` avoids duplicate text. The header reserves 72px beyond its normal inset, and traffic-light positioning uses logical coordinates. The override repeats window dimensions because Tauri merges the windows array as a replacement. Native alignment/fullscreen behavior needs macOS QA. Tauri documents that overlay title bars may require initial focus before dragging; title/control placement can vary by macOS version.
- Windows retains Tauri's taskbar/resizable window behavior and OS handling of keyboard/window-manager operations. Native Windows Win+Arrow, Alt+Space, Alt+F4, drag-from-maximized and Snap integration require target testing. A custom HTML maximize button does not implement Windows 11's native hover Snap Layout flyout; no extra native plugin was introduced. Native Linux window managers other than this WSLg/XWayland session, and Wayland, require release QA.

## Native WSLg test boundary

- XTest delivers trusted clicks and keyboard input, but its synthesized motion did not drive WSLg's Windows-side move/resize loop. A test-only PowerShell/User32 pointer driver exercised that loop successfully: dragging changes actual position, and edge/corner drags change actual dimensions. Production has no PowerShell, X11, or P/Invoke integration.
- Minimize succeeded according to the host's `IsIconic` while GTK/Tauri `isMinimized()` remained false and X11 still reported a viewable window. External host restore retained pane focus. This matches [WSLg issue 1511](https://github.com/microsoft/wslg/issues/1511); tests record both measurements rather than treating the GTK flag as authoritative under WSLg.
- The host driver identifies only the exact Qpanes title and enumerates minimized windows; WSLg can host multiple Linux windows in one RDP process. Its pointer coordinates account for host shadow margins. It changes only the tested window/cursor, restores its temporary thread DPI context, and never changes execution policy or app capabilities.
